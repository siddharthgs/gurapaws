# Gurfan 🐾

A digital-native dog adoption platform for **Hyderabad** — built to scale across India.

Gurfan is a two-sided platform: shelters, NGOs, and independent rescuers list adoptable dogs (supply); adopters browse and apply (demand). The goal is to make listing and adopting radically faster than today's WhatsApp-and-Instagram status quo.

> **Status:** R0.2 — Core data model + persistence (Dog / Lister / Adopter / Application) on Drizzle + Postgres. ([GURA-3](/GURA/issues/GURA-3))

## Stack

| Layer         | Choice                           | Why                                                                            |
| ------------- | -------------------------------- | ------------------------------------------------------------------------------ |
| Framework     | **Next.js 15** (App Router, TS)  | Boring, proven full-stack React. UI + API routes in one codebase.              |
| Styling       | **Tailwind CSS v4**              | Fast, consistent UI without bespoke CSS; low maintenance.                      |
| Language      | **TypeScript**                   | Type safety across the data model as the platform grows.                       |
| Persistence   | **Postgres** via **Drizzle ORM** | Relational fit for Dog / Lister / Adopter / Application; type-safe migrations. |
| Local DB      | **PGlite** (embedded Postgres)   | Real Postgres dialect, zero infra to run locally; same migrations as prod.     |
| Hosting (now) | **GitHub Pages** (static export) | A real public URL with zero extra infra for the hello-world phase.             |
| CI/CD         | **GitHub Actions**               | Build + lint on every push; auto-deploy from `main`.                           |

**Rationale (1 line):** Next.js + TypeScript + Tailwind is the leanest proven full-stack combo — fast to ship, low ops, and the same codebase carries us from a static landing page to a server-rendered marketplace with API routes and Postgres, no rewrite.

## Data model & database

The whole product runs on four entities (see [`src/db/schema.ts`](src/db/schema.ts)):

- **`listers`** — supply side: shelters, NGOs, and independent rescuers (one table, discriminated by `type`).
- **`adopters`** — demand side.
- **`dogs`** — the listings, each owned by a lister (`name`, `breed`, `size`, `ageMonths`, `sex`, `temperament[]`, `photos[]`, `status`, `city`/`area`, plus a shareable `slug`).
- **`applications`** — the two-sided link: an adopter applies for a dog, with a `status`. Unique per `(dog, adopter)`.

Local dev uses **PGlite** (embedded Postgres, written to gitignored `./.pglite`) — no server to install. Migrations are real Postgres SQL generated by drizzle-kit, so production is a connection-string swap to managed Postgres (Neon / Vercel / Supabase), not a rewrite.

```bash
npm run db:generate   # regenerate SQL migration from schema.ts (after edits)
npm run db:migrate    # apply migrations to the local PGlite db
npm run db:seed       # load realistic Hyderabad sample data (idempotent)
npm run db:check      # read-path proof: browse feed + applications inbox
npm run db:reset      # migrate + seed in one go
```

**Future network-effect hooks** (shareable profiles, adoption stories, foster/volunteer/donate intent) slot in as _new tables_ referencing these four — `dogs.slug`, UUID keys, and timestamps are already in place, so no rewrite is needed.

## Deploy

Every push runs **build + lint**. Pushes to `main` additionally build a static export (`output: 'export'`) and publish to GitHub Pages.

**Live URL:** https://siddharthgs.github.io/gurapaws/

### Note on hosting evolution

GitHub Pages is static-only — perfect for this landing-page phase with zero infra cost. When R1.2 (adoption application flow) and the shelter portal need server-side rendering, API routes, and a database, we move hosting to **Vercel** (or Fly.io). That is a **host swap, not a stack rewrite** — the Next.js codebase is unchanged. A deploy token for the server host will be requested from the CEO when that phase begins.
